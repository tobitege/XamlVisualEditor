# Changelog

All notable changes to XamlVisualEditor are documented in this file. The project
uses Semantic Versioning.

## [0.4.0] - 2026-10-28

### Added

- `TerminalEnvironment.CaptureStartup()` records the environment the host process was started with, and both PTY providers start the shell from it with the overrides of `TerminalSessionOptions.Environment` applied. The editor captures it first thing at startup, so variables it sets for itself later, such as the MSBuild paths it registers for loading projects, no longer reach the shell, and `dotnet build` in a terminal uses the SDK the repository selects. A host that does not call `CaptureStartup()` keeps the current process environment.
- Options › Terminal sets the font families and the font size of the terminal, on every platform. The families are a comma-separated list of which the terminal uses the first installed one; an empty list restores the default `Cascadia Mono, Menlo, Consolas, monospace`, and the size is limited to 6 to 72. Open terminals take a saved change at once. `ITerminalViewModel` has the members `FontFamilies` and `FontSize`, with these defaults for existing implementations, `TerminalFont` holds the defaults and limits, and `FontFamilyListConverter` turns such a list into a `FontFamily` for bindings. `TerminalControl` defaults to the same list instead of Cascadia Mono alone.
- `IEditorServices.ApplyWorkspaceEditAsync` applies a workspace edit through the editor documents and returns whether a document changed, and `IEditorServices.OpenDocumentsChanged` reports opened and closed documents, also those that do not become the active document. Both have defaults for existing implementations: no workspace edits and no event.
- `SyncEngine.ReplaceText` replaces the text of a designer document as one undo entry together with changes of related text documents, which the same undo restores; `SyncEngine.CanReplaceText` tells whether an unfinished edit prevents it.
- A new `XamlLanguageService` constructor takes an `IDesignerCodeBehindRefactoringService` and the unsaved texts of open C# documents. `DesignerCodeBehindRenameRequest.Member` selects a control or an event handler, and a request without `ProjectPath` uses the project that lists `DesignerCodeBehindRenameRequest.XamlFilePath` among its additional files, as Avalonia projects do with their AXAML files. `DesignerCodeBehindRenamePlanner.CreateAsync` plans such a request in a solution.

### Changed

- The German user interface translates the remaining English texts: the Discard button, the change status of the Git Changes panel (for example "Staged hinzugefügt" or "Unstaged mit Konflikt") and the Capabilities column of the extension manager. The messages of the designer and the previewer when an insert, paste, duplicate, delete, move, resize, arrange, rename, refactoring undo or event handler assignment is refused, the errors of the property structure editor and of property values that do not fit their type, of the previewer connection, of reading toolbox controls, of the template list, of a force push without upstream, of continuing a finished Git operation, of starting a debug adapter and of the ACP agent connection and prompts come from `UiStrings` and follow the language of the editor. Git terms such as Branch, Commit, Stash, Staged and Upstream stay English. The designer and the previewer now ask with the same text to wait for the layout measurements of the previewer, and distributing controls in a Grid in the previewer names the number of rows or columns it needs, as the designer does.
- An empty value in `TerminalSessionOptions.Environment` removes the variable; it used to set the variable to an empty value. Without an override for `TERM` or `COLORTERM`, Linux and macOS set them to `xterm-256color` and `truecolor` as before, and Windows only adds them when they are missing.
- Terminals on Linux and macOS no longer inherit `TMUX`, `TMUX_PANE`, `STY`, `WINDOW`, `WINDOWID`, `TERMCAP`, `COLUMNS` and `LINES`, so `tmux` and `screen` also start in the terminal of an editor that was itself started inside one of them.
- Closing a terminal on Linux or macOS hangs up its shell, and on macOS kills a shell that is still running after a short grace period; the shell is collected after it exits. The close runs on the thread pool and does not block the window. On Linux the kernel window size of the terminal no longer carries the pixel size; the emulator still answers pixel size queries.
- `XamlVisualEditor.Terminal` depends on [Porta.Pty](https://github.com/tomlm/Porta.Pty) and, through it, on `Microsoft.Windows.Console.ConPTY`. Windows keeps the in-box ConPTY, and projects that reference the terminal do not get the `OpenConsole.exe` host copied to their output.
- `XamlEditorDockFactory.AddDocument` and `AddTextDocument` take an optional `activate` parameter; without activation the document is added behind the active one. Compiled callers need to be rebuilt.

### Removed

- The public constructor of `UnixPtyProcess`, which took the process id and the file descriptor of a PTY created outside the provider; `UnixPtyProvider.StartProcess` creates the process.

### Fixed

- The selection pipe of a compact tab, such as Staged and Unstaged in the Git Changes panel, is drawn below the header text instead of through it
- Opening a terminal on Linux or macOS no longer crashes the editor at a later, random point. The terminal forked the editor process and ran .NET code in the child before it started the shell; with W^X, which .NET enables by default since .NET 7, the child shared the executable code memory of the editor and overwrote it. `UnixPtyProvider` now starts the shell through Porta.Pty, which forks and executes in native code and resizes on macOS without running `stty`. The PTY tests also run in CI.
- The terminal uses the first installed font of its font list, such as `monospace` on Linux, instead of only trying the first one. Where Cascadia Mono was missing it fell back to a proportional font, sized its cells for the widest letter and drew the text with gaps between narrow letters.
- A rename or a code action that changes an AXAML or XAML file changes it. The edit used to reach only plain text documents, so the change of a designer document was lost while the status reported it as applied. A designer document now gets the change in the code area and the document structure as one undo step; the changes of text documents in the same edit belong to the step of the first designer document, and each further designer document has its own step. A closed file opens without becoming the active document, an edit whose documents changed in the meantime changes none of them, the status reports a rename or a code action only when a document changed, and source control checks out a file opened this way on its first change. The extension API applies code actions the same way.
- Renaming an `x:Name` or an event handler through the XAML language service changes the `#name` references in style selectors and bindings, every event attribute of that handler, and with code-behind the generated field, its uses, the `FindControl` lookups and the handler methods in C#. It used to change only the attributes of the AXAML file, which left the project unable to build, and treated any attribute that starts with a capital letter as an event. Names and handlers are renamed only in AXAML without errors. Without a C# workspace, as in the XAML language server, names and handlers of a document with `x:Class` are not renamed, and the language server answers a refused rename with an error that names the reason.
- Renaming a control in the designer of a loaded project renames the generated field, its uses and the `FindControl` lookups in the code-behind. The designer compared the AXAML files of the projects with the document path in a way that never matched, so it never found the project of the document, renamed only the AXAML and left the code-behind unable to build. A closed code-behind opens without becoming the active document, and the rename waits for the C# workspace to load and is refused when it cannot be loaded. Assigning an event handler in the designer uses the project of the AXAML file too, and refuses a file that several projects list.
- Binding path completion suggests the members of the nearest `x:DataType` around the caret, or of the `DataType` of a data template, instead of the first `x:DataType` in the document, and none inside a data template without a type. A `>` in an attribute value or a comment no longer ends the element for completion.

## [0.3.0] - 2026-10-18

### Added

- The Git extension shows the branch of the workspace repository in the status bar, with the commits ahead of and behind its upstream and the number of changed files, for example `main ↑1 ↓2 · 5`; a click opens the Git Changes panel. The panel is listed under View › Panels, Ctrl+Shift+G opens it, and the Extensions › Git submenu and the Command Palette offer refresh, the "Git" output channel, stage all, unstage all, commit and creating a repository. Stage, unstage and discard (after a confirmation) are also in the Git submenu of the editor context menu and work on the active document; the output channel lists every git command the extension runs, with user names and passwords in URLs masked. Extensions can read the context keys `git.available`, `git.isRepository`, `git.hasRemote`, `git.hasUpstream`, `git.isMerging`, `git.hasConflicts` and `git.autoRefresh`.
- The Git extension has a Git Repository panel, listed under View › Panels on the left, whose Branches tab lists the local and the remote branches, marks the current branch, shows the commits ahead of and behind its upstream or "gone" when the upstream was deleted, and names the commit of a detached HEAD. It reads the branches only while it is visible and again only when branches or HEAD change. Its context menu switches to a branch, creates a branch from it and deletes it; its buttons refresh, fetch, pull, push, synchronize and create a branch. The Extensions › Git submenu and the Command Palette offer switching a branch from a list, creating a branch with or without switching to it, deleting a branch (after a confirmation, and after a second one when it is not fully merged), fetch, pull, push and synchronize (pull, then push). Switching to a remote branch switches to the local branch that tracks it, under any name, or creates one; when a local branch of the same name tracks something else, it asks whether to switch to that branch, create a new branch or check out the commit without a branch. A new branch created from a remote branch of the same name tracks it when `branch.autoSetupMerge` lets it, as by default; any other new branch has no upstream until its first push. A branch name that Git does not accept is reported before Git runs. Fetch runs `git fetch` for every remote except one with `remote.<name>.skipFetchAll`, so the configured refspecs, such as notes or tags, and the pruning of `fetch.prune` and `remote.<name>.prune` apply; when pruning removes a remote branch, the local branches that tracked it show their upstream as gone. A remote that fails does not stop the others, and the message names the fetched ones. Fetch, pull and push show a progress dialog that cancels them, stop after ten minutes, never wait for a password prompt, do not hold up staging or committing while they wait for the network, and explain failed sign-ins, missing access rights, unreachable servers, unknown SSH host keys, pushes behind the remote, pushes refused by a protected branch or server hook, and diverged branches; the message shows the explanation and the decisive line of Git's output with the indented lines that belong to it, such as the files a pull would overwrite, and points to the "Git" output channel, which keeps the complete output, whenever Git wrote any. Pull fetches the remote of the upstream branch as `git pull` does, with its configured refspecs, tags and pruning, then only fast-forwards, and says how many commits it brought or that the branch was already up to date; cancelling stops the fetch and the wait for another running Git command, never the fast-forward. When the upstream branch no longer exists on the remote, for example because it was deleted after a merge, pull and synchronize explain it whether or not fetching prunes, and synchronize does not push, so it does not create the deleted branch again; the status bar tooltip shows the upstream as gone once a pruning fetch removed its remote branch. When the push of a synchronization fails, the message says that the pull completed. Pushing a branch without upstream asks before it pushes to `origin` and sets the upstream.
- The Git extension has a Git History panel, listed under View › Panels at the bottom, that lists the commits of the whole repository, of a file or of a folder, newest first and 100 at a time with "Load More", with the branches and tags that point to them. It filters by a text of the commit message and by author name or email, both ignoring case, with the authors of the listed commits offered as suggestions; a new filter or scope cancels a running read. A refresh, a change of HEAD or the branches and showing the panel again read the listed commits again, as many as were loaded, and keep the selected commit; all pages of a history start at the same commit, also when the history starts at a branch, so a commit made in between neither repeats nor shifts rows. The history of a file follows its renames, also over several pages. The selected commit shows its message, author, committer, parents and changed files, a merge commit compared with its first parent; the selected file shows its diff with old and new line numbers and buttons to the previous and next change, and a diff is read only up to 20,000 lines or 4 MiB, so a minified file is not read completely either, and then cut with a notice. The context menus copy the commit id or the file path, create a branch at the commit and show the history of a file starting at the selected commit. "Show Repository History" in the Extensions › Git submenu and the Command Palette opens the panel, and "Show History" in the Git submenu of the editor context menu shows the history of the active document. "Show Repository History" takes a commit, branch or tag to start at as argument; "Show History" takes a file or folder path and, as second argument, a commit, branch or tag to start at. The Git Repository panel has a Tags tab that lists the tags, newest first, with their commit, date and message; its context menu and a double-click show the history starting at a tag, and its context menu creates a branch from it. A tag of a tree or a blob shows the type of its object instead of a commit and offers neither. The date columns of the history and the tags fit any date and time in English, German and the current culture in the font of the cells. A row copied with Ctrl+C holds every column, including the message, the date, the tag name and the change status, and the branch names show their full name in the tooltip. `GitService` implements the new `IGitHistoryService` (`GetLogAsync`, `ResolveCommitAsync`, `GetCommitAsync`, `GetCommitFileDiffAsync`, `GetTagsAsync`), and the new project `XamlVisualEditor.SourceControl.UI` holds the `UnifiedDiffEditor`, the light and dark default diff colors of `DiffColors`, which the diff of the Git Changes panel uses too and which an application or theme overrides by defining brushes under the keys of `DiffColors`, such as `DiffAddedForegroundBrush`, and the data grid behaviors for source control panels.
- Extensions can add items to the context menus of the explorers and of document tabs through the menu locations `ExtensionMenuLocations.ExplorerContext` (`menu.explorer.context`) and `ExtensionMenuLocations.DocumentTabContext` (`menu.documentTab.context`). The items follow the fixed items, also in submenus, and their command receives the full path of the clicked file or folder or of the file of the tab as argument 0; a project node in the Solution Explorer passes its project folder, and the items are hidden on nodes and tabs without a path. Extensions can colour files and folders in the File Explorer, the Solution Explorer and the extension trees whose items implement `IExtensionTreeItemPathProvider` through the new `ExtensionContext.ExplorerDecorations` (`IExplorerDecorations`): a layer from `CreateLayer()` takes full paths with an `ExplorerDecoration` of a colour class (`Modified`, `Added`, `Deleted`, `Conflicted`), an optional badge and its tooltip, and the host draws them with theme brushes for the light and the dark theme.
- The Git extension shows the Git status in the explorers: a changed file gets the colour and letter of its change (M, A, U, R, D, or ! for a conflict), and every folder above a change the colour of a modification, or of a conflict when a conflict lies below it; a new untracked folder is marked as a whole. Extensions › Git › Show Git Status in Explorers switches it off and on and is remembered, with the context key `git.explorerDecorations`. Stage, unstage, discard and show history are in the Git submenu of the explorer context menus, and stage, unstage and show history in that of the document tab context menu.
- Extensions can mark lines in the text and code editors through `ITextEditorViewHost.CreateLineMarkLayer(clickCommandId)`: a layer takes `TextEditorLineMark`s (`Added`, `Modified`, `Deleted`) per full path, the editors draw them in a margin after the line numbers with the theme brushes `SourceControlAddedBrush`, `SourceControlModifiedBrush` and `SourceControlDeletedBrush`, which the explorer decorations use too together with `SourceControlConflictedBrush`, and a click runs the command of the layer with the path and the line. `IExtensionViewHost.ShowDocumentAsync` opens a document tab with the content an extension returns, a control or a view model of a built-in extension, or activates the open tab of the same id; such tabs are not saved in the layout, and closing one disposes its content. `IEditorDocument.GetTextAsync` can be called from any thread. `GitService` implements the new `IGitContentService` (`GetFileContentAsync` of the index or HEAD, `GetBlameAsync`), `GitFileChange.IndexObjectId` holds the object id of a file in the index, `LineDiff` compares line lists, `DiffLineBuilder.FromLineDiff` shows such a comparison in the `UnifiedDiffEditor`, and `SharedFileReader.Decode` decodes file bytes as the editor does.
- The Git extension marks the lines of every open document that differ from the staged version, as `git add` would take them: added and modified lines and the places of removed lines, updated 300 ms after typing stops and after staging, committing or switching branches. A click on a mark opens the comparison with the staged version at that change. Extensions › Git › Show Git Changes in Editors switches the marks off and on and is remembered, with the context key `git.changeMarkers`. "Compare with HEAD" and "Compare with Staged" in the Git submenus of the editor, explorer and document tab context menus and in the Command Palette open a document tab that compares the file, as typed so far, with its version in HEAD or the index, with one hunk per change, buttons to the previous and next change, the whole file and comparing again; a file without such a text version, such as an untracked, conflicted, binary, Git LFS or larger than 16 MiB file, shows a note instead, and so does a file whose lines are equal while Git reports a change of its line endings, byte order mark or final newline. "Blame" opens a document tab that lists the commit, author and date of every line of the saved file; a double-click or Enter shows the commit of a line in the Git History panel.
- `IOutputChannel.Show()` of an extension shows the Output panel in front with that channel selected. The panel learns of it through the new `IWindow.OutputChannelShowRequested` event; its default implementation never raises it, so existing implementations of `IWindow` keep working.
- The Git Changes panel stages, unstages and discards single lines and hunks: "Stage Selected Lines", "Unstage Selected Lines" and "Discard Selected Lines…" above the diff work on the selected lines or, without a selection, on the hunk at the cursor; discarding asks first. They are also the commands `git.stageSelection`, `git.unstageSelection` and `git.discardSelection`. The diff is read again before git applies the lines, and a diff that changed in the meantime is reloaded instead of applied; line endings, the encoding and the mode of the file are kept, and a selection that would join a last line without line break with another line is refused. Untracked files and files with conflicts are only staged or discarded as a whole. `IGitPatchService` (`GitServiceSet.Patch`) applies a `GitDiffSelection` and amends commits; `GitPatchBuilder` builds the patch from the bytes of the diff.
- The Git Changes panel amends the last commit while "Amend last commit" is checked, also with a changed message only; checking it fills in the message of the last commit, and amending a commit that the upstream already contains asks first, because the branch then needs a force push. `git.commitAmend` shows the panel with the box checked. The commit message box takes several lines.
- The Git Repository panel has a Stashes tab that lists the stashes with message and date and stashes the changes, with or without the untracked files, and applies, pops or drops the selected stash; dropping asks first, a stash that applied with conflicts is kept and that is reported. The commands are `git.stash`, `git.stashIncludeUntracked`, `git.stashApply`, `git.stashPop` and `git.stashDrop`, the last three with a list to pick from in the Command Palette. Pop and drop check that the stash is still at its position in the list. `IGitStashService` (`GitServiceSet.Stash`) lists and changes the stashes.
- "Merge Branch…" in the Extensions › Git submenu and the Command Palette merges a branch picked from a list, or the branch given as argument, into the current branch with `git merge --no-edit`, and says whether it merged, was already up to date or stopped. A merge that stopped shows the Git Changes panel.
- Conflicts of a merge, rebase, cherry-pick, revert or patch application are resolved in the editor: while one of them is in progress, the status bar shows it with the number of conflicts, for example `main · 3 · Merging ⚠2`, and the Git Changes panel shows a banner with the operation, what is left to do, "Abort" and, except for a merge, "Continue". Conflicted files are listed under Conflicts with how each side changed them, no longer as changes, with "Open", "Ours", "Theirs" and "Mark Resolved". "Ours" and "Theirs" ask first and take that side's version of the whole file, deleting it when that side deleted it, and "Mark Resolved" stages the file and asks first while its saved text still contains conflict markers. Staging a file, a folder or all changes no longer stages a conflicted file. The editors mark every conflict block of an open conflicted file with `SourceControlConflictedBrush`. A click on the mark picks ours, theirs or both, which replaces the block in the buffer as one undo step. During a merge the commit message box is filled with the message git prepared, and a merge can be committed with nothing staged. Commit waits until no conflicts are left. A rebase, a patch application, a cherry-pick and a revert commit their steps with "Continue", so Commit and Amend are unavailable during them, except at an edit step of a rebase. A sequence of picks or reverts stays detected after one of its steps was committed on the command line. The commands are `git.abort`, `git.continue`, `git.acceptOurs`, `git.acceptTheirs`, `git.markResolved` and `git.resolveConflict`, the conflict commands also in the Git submenus of the editor and explorer context menus. Stash and merge are unavailable during an operation, because a stash would end a resolved merge without its merge commit. The new context key `git.operationInProgress` is set during an operation. `IGitMergeService` (`GitServiceSet.Merge`) merges, aborts and continues the operation in progress, takes one side of conflicted files and reads the prepared commit message. `GitRepositoryOperation` gains `ApplyingPatches`, `GitRepositoryStatus` gains `IsStoppedForEdit` and `TextEditorLineMarkKind` gains `Conflict`.
- Questions and long git commands of the Git extension can no longer lose data by an unclear answer. A destructive confirmation starts on its cancel button, so Enter or Space cancels, and "Mark Resolved" over conflict markers, a merge picked from the list and the other destructive questions all are destructive. Cancelling a progress or closing the editor no longer kills a writing git command half way, which could leave `index.lock` behind and a half updated working tree. Only a commit and an amend stay cancellable while their hooks run. A writing command that runs longer than a second shows a progress, which after 15 seconds and while a writing command runs offers "Stop git…" for a command that hangs, for example in a hook. Only a confirmed stop ends git, also a pull whose fast-forward hangs after its cancel, and the message says that the command may be half done. Closing the editor, also with File › Exit, waits for the writing git commands with a progress, because a command whose output the editor closed can still fail; after 15 seconds its button closes anyway after a destructive confirmation, and its window button and Escape keep the editor open. `ProgressDialogRequest.CancelDelay` shows the cancel button, and lets the window button cancel, only once the delay elapsed, `ProgressDialogRequest.CancelAvailable` only while it last said true, and a `GitProcessStop` scope counts the writing commands that a confirmed stop ends and reports through `Writing` whether one runs. A sync cancelled after its pull says that the pull happened. Abort changes nothing when the operation changed while the question was open, and `IGitMergeService.AbortAsync` takes the confirmed operation and returns whether it aborted. "Clear All" drops each confirmed stash after checking it, so a stash made meanwhile stays. Taking a side refuses files with unsaved changes in the editor.
- "Rename Branch…" in the Extensions › Git submenu, the Command Palette and the context menu of a local branch in the Branches tab renames a local branch. The new name is checked as for a new branch, and git moves the upstream and the other settings of the branch along. The command is `git.renameBranch`, and `IGitBranchService.RenameAsync` renames a branch.
- The Git Repository panel has a Remotes tab that lists the remotes with their URL, without the user name, password or token a URL may contain, and adds a remote, changes its URL, renames it with its remote-tracking branches and removes it after a confirmation. A remote name that starts with "-" is refused, and fetch and push pass a remote name so that git never reads it as an option. The application log masks credentials in failed git commands as the Git output channel does. The commands are `git.addRemote`, `git.setRemoteUrl`, `git.renameRemote` and `git.removeRemote`, also in the Extensions › Git submenu and the Command Palette. `IGitRemoteService` gains `AddRemoteAsync`, `RenameRemoteAsync`, `RemoveRemoteAsync` and `SetRemoteUrlAsync`.
- A stash opens in a document tab with its files and their diffs, by a double-click or "Show" in the Stashes tab or with `git.stashShow`. Untracked files of the stash show as added. The Stashes tab also creates a branch from a stash at the commit the stash was made on and applies and removes the stash there (`git.stashBranch`), and it drops every stash after a confirmation (`git.stashClear`). `IGitStashService` gains `BranchAsync`.
- The banner of a rebase, cherry-pick, revert or patch application in the Git Changes panel has "Skip", which skips the current step after a confirmation, for example a step that became empty after its conflicts were resolved, and skips nothing when the operation went on to another step meanwhile. The question of a rebase says that git also discards the other uncommitted changes of tracked files. The context menu of the Git History panel cherry-picks or reverts the selected commit, and a cherry-pick or revert that stops shows the Git Changes panel. The commands are `git.skip`, `git.cherryPick` and `git.revert`, and `IGitMergeService` gains `SkipAsync`, `CherryPickAsync` and `RevertAsync`.
- The Tags tab of the Git Repository panel creates a tag at HEAD, annotated with an entered message or lightweight without one, pushes the selected tag to a remote and deletes it locally or on a remote, both after a confirmation; "New Tag Here…" in the context menu of the Git History panel creates one at the selected commit. A push of a tag that the remote has at another commit is refused and says so. The commands are `git.createTag`, `git.pushTag`, `git.deleteTag` and `git.deleteRemoteTag`, `IGitBranchService` gains `CreateTagAsync` and `DeleteTagAsync`, and `IGitRemoteService` gains `PushTagAsync` and `DeleteRemoteTagAsync`.
- "Rebase Current Branch…" rebases the current branch onto a branch picked from a list after a confirmation that says that a pushed branch then needs a force push, and a rebase that stops shows the Git Changes panel. The context menu of a branch in the Branches tab merges it into the current branch or rebases the current branch onto it. A push that the remote rejects asks with git's reason whether to force push, which fits after an amend or a rebase while pulling keeps the remote's commits, and "Force Push…" asks the same directly. The question is destructive, and the force push replaces only the upstream branch of the named branch and only while it still points to the commit known when the question opened, whatever `push.default` says; it is offered only when a push of the branch goes to that upstream branch on a remote. The commands are `git.rebase` and `git.forcePush`, `IGitMergeService` gains `RebaseAsync` and `IGitRemoteService` gains `ForcePushAsync` and `GetForcePushLeaseAsync`.
- The Git submenu of the editor, explorer and document tab context menus stashes the changes of a file or folder, including its untracked files, and "Stash Staged Changes…" in the Stashes tab and the Extensions › Git submenu stashes only the staged changes, which needs Git 2.35 or newer; when git saves the stash but cannot remove its changes, the message says so. The commands are `git.stashPaths` and `git.stashStaged`, and `IGitStashService` gains `PushPathsAsync` and `PushStagedAsync`.
- "Compare with Current Branch…" in the Extensions › Git submenu and in the context menus of a branch or a tag in the Git Repository panel opens a document tab with the files and diffs that the current branch changed since it and the other branch or tag went their own way, and lists the commits that only one of them has. The command is `git.compareBranches`, and `IGitHistoryService` gains `GetMergeBaseAsync`.

### Changed

- `FileSystemPathComparison` ignores the case of paths on macOS as on Windows, because the file systems of both ignore it; before, a path whose case differed from the one git or the workspace knew was another path there.
- `GitPanelViewModel.DiffLines` is an `IReadOnlyList<DiffLine>` that is replaced for every shown diff instead of an `ObservableCollection<GitDiffLineViewModel>`, and the diff of the Git Changes panel is a `UnifiedDiffEditor` with the colours of the theme. The diff of the panel ignores `diff.external` and textconv attributes and always uses the `a/` and `b/` prefixes, whatever `diff.noprefix` or `diff.mnemonicPrefix` say.

- The text of message dialogs, the information, warning and error messages of the editor and of extensions, can be selected; Ctrl+C copies the selection, and Copy in its context menu copies the selection or, without one, the whole message.
- The Command Palette lists only the commands that are enabled as their menu items are, whose `When` clause holds and that the editor can run at the moment, and does not run a selected command that is no longer enabled.
- The Git commands need Git 2.26 or newer. On Windows, `GitService` starts the git of a Git for Windows installation directly instead of its `cmd\git.exe` launcher, also when `GitProcessOptions.ExecutablePath` or a scoop shim names the launcher, and gives it the environment the launcher sets, so cancelling reaches every process git started. `GitService` passes the paths of stage, unstage and discard through standard input, so staging and unstaging all changes also work with thousands of files, and its `GetStatusAsync` throws `InvalidOperationException` with Git's error output instead of returning a status whose `IsRepository` is false. `GitRepositoryStatus` and `GitFileChange` are records that compare by value. `GitStatusParser.ParseStatus` (porcelain v1) is obsolete.
- When reading the Git status fails, for example because of a damaged index, the Git panel and the status bar show Git's error, the repository stays open and the status is read again on its next change. A linked worktree refreshes when its branch moves in the shared repository. A commit shows a progress dialog that cancels it, for example while a slow pre-commit hook runs; cancelling also ends the processes the hook started, and a commit whose hook left a process running still completes. The diff of the selected file reloads when the file changes while its status stays the same, and a diff that finishes loading after another file was selected is not shown; a deleted repository is shown as no repository after the next refresh, and staging a file or folder whose path differs in case from Git's path stages its changes. Unstaging a renamed file also unstages the deletion of its old name, and a conflicted file is listed only under the changes, where staging marks it as resolved.

- The Git panel shows the status without being switched on first: the status refreshes when the git folder changes, for example after a branch switch in a terminal, and after every Git command of the editor.
